# Interactive commands and defaults

Move choices that belong to the person using the client; keep accepted multi-step operations and their recovery in bridge services. Closing a tab after an accepted assignment, workspace creation or finish must not stop the operation. The client may collect input across screens, but it must not become the durable workflow coordinator.

## Command lifecycle

This is the target for operations that gain the P2 receipt/recovery capability. Today receipt coverage is method-specific. Before negotiation, retain existing operation IDs and uncertain-result handling; do not invent a receipt query, automatic retry or universal journal for legacy methods.

1. Read cached facts and capabilities. Collect and validate input for immediate feedback; never treat this check as device authorization.
2. Mint one stable operation ID for the intended action. Write a provisional/queued display record through the cache API, with scope and user intent. Unsent bodies/drafts are not disposable replica data.
3. Submit a typed command through the protocol adapter. A new precondition or cleanup option must be explicitly supported; old bridges can silently drop unknown parameters.
4. Normalize the ACK into the same cache ingestion path as events. ACK means what its typed state says: accepted, completed, refused or uncertain; acceptance is not completion.
5. On lost response, query the operation receipt before resending. Reconcile provisional state by operation ID. The bridge owns execution after acceptance; the client owns cancellation requests and displaying the result.

Keep bounded composite commands where several local steps must succeed or recover together. The goal is not an RPC for each filesystem syscall. A client-side wizard can be resumed from a draft; accepted git/agent operations need device-owned recovery. Preserve existing method-specific journals and add missing intent/checkpoint coverage before promising automatic restart recovery for another operation family.

The audit's branchFinish mismatch has its own follow-up: [client branchFinish](../../../spa/src/core/branchFinish.js) describes deletion while [the legacy finish adapter](../../../bridge/src/app/workspaces/mod.rs#L648) invokes workspace completion. Use the resolved contract before changing this flow; never infer semantics from an accepted but ignored parameter.

## Acceptance and release

Test user and MCP calls against the same service behavior, two clients choosing the same target, stale cached blockers, duplicate requests, disconnect before ACK, and tab closure after acceptance. Preserve pending/uncertain display and all original operation identity fields. Do not broaden cleanup defaults or close issues as a side effect of rendering.

P1 is app-only. Missing explicit parameters and durable operation semantics require bridge + app in P2; internal extraction is P3 and can preserve the existing wire. Changes to canonical preferences, supported enums or autonomous default rules still require an appropriate bridge change. See [always-on services](04-always-on-services.md) for the reclassified decisions and [contracts/cache](02-contracts-and-cache.md) for compatibility.
