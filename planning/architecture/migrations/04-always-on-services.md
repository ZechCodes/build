# Always-on bridge services

The SPA owns interaction choices that can be made while it is open. Work triggered by an agent, a timer, a provider response, or a persisted intent must continue when the browser closes. Keep that work in the bridge, but move its decisions out of RPC handlers and event publishers into typed services. No separately shipped policy runtime or client-installed executable policy is proposed. Normal user prompts and supported configuration remain inputs; autonomous prompt assembly remains bridge policy.

## Boundary

The proposed home is `bridge/src/services/{agents,tracker,routing,workspaces,notifications}`. A service accepts typed commands and domain events, reads through repositories, and invokes narrow device/provider adapters. RPC handlers translate wire input into typed commands and serialize results; event publishers observe committed facts. Neither layer decides what the next agent or tracker action is. A service may publish a typed change after its write commits; the transport then pushes it. The SPA follows the #82 flow: pull/events update its cache, cache emits a change notification, and views reread the cache. P0 internal typed contracts precede each P3 extraction; P2 factual replication is needed only for slices changing the wire/client facts. Internal extraction can preserve the current wire independently of P2. Legacy cleanup is P4.

The durable owner of a pending action is the device. Preserve existing operation IDs and receipts; extend intent/checkpoint coverage where the target service needs restart recovery that is not implemented today. Persist intent before dispatch and reconcile its journal before retrying. Provider delivery and filesystem/git operations use claims, off-lock execution and recovery choreography; only related SQLite records can share a database transaction. The SPA may set user preferences, but the bridge validates and stores the value before an always-on service uses it.

## Sequence and proof

1. Define typed commands, events, repositories, and adapters in `services` without accepting `serde_json::Value`, method strings, socket handles, or UI cache objects. Keep existing RPC names and result shapes while handlers become translators. Cover direct MCP with the same typed command path and its stricter identity checks.
2. Extract the agent prompt and delivery service first. Verify cold/warm text, catch-up order and size, delivery receipts, uncertain outcomes, compaction ordering, and provider reset retry with the browser disconnected and after bridge restart.
3. Extract tracker assignment, report reactions, notices, and routing. Exercise agent-to-agent assignment, new workspace provisioning, one-turn issue auto-move, tracker notice dedupe, capture route single-flight, and restart at every persisted boundary. The service emits committed facts; transport changes only how they are sent.
4. In P4, keep or remove compatibility reads for retired singular Issue/Plan records according to data-retention requirements. [`app/rpc.rs::retired_planning_operation`](../../../bridge/src/app/rpc.rs) rejects their mutations, and [`app/issues/scheduler.rs::ensure_issue_scheduler_available`](../../../bridge/src/app/issues/scheduler.rs) rejects scheduling. Treat that code as compatibility/deletion work, not a new service to port.

The cutover passes when closing every browser tab mid-agent turn, mid-assignment, and during a settle/retry timer does not stop the work; reopening only pulls the committed result into cache. It must preserve scoped MCP authorization, single-owner claims, durable operation identity, idempotent local effects and honest uncertain states where the provider result cannot be proven. Prove restart recovery per operation family before advertising it; do not imply exactly-once external delivery.
