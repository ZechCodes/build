Direct Connection Spec

Status: draft for review (2026-09-15). Companion to Strict P2P Transport Spec.md (binding for the hosted path) and E2EE Platform Scope.md. Scope of this revision: Tailscale only.

A direct connection is a browser talking to a bridge with nothing of Build's in the path: no relay, no api, no Cloudflare, no login. The bridge serves the web app itself, authenticates the browser itself, and is reachable because the phone or laptop is on the same tailnet as the machine it runs on. It is a fully owned security guarantee: the user's tailnet is the perimeter, and the bridge's own key registry is the door.

Guarantee. A direct device never falls back to, consults, or is discoverable through Build infrastructure. If the direct path is down, the device is away. There is no other path.

1. Goals and non-goals

Goals

  • Open the Build web app on a phone or laptop against a bridge on the same tailnet with no Build account and no Build server involved.
  • Keep the existing SPA and its E2EE session protocol; the browser is the client, no native app.
  • Authentication and key pinning are owned by the bridge: an invite pairs a browser once, and the bridge keeps a revocable list of authorized clients.
  • The tailnet is defence in depth, not the authentication: a stranger who reaches the port still cannot open a session.

Non-goals (this revision)

  • Bare-LAN operation without Tailscale (the TLS trust bootstrap is the blocker; see §7).
  • NAT traversal, WebRTC, STUN or TURN on the direct path. A tailnet address is reachable, so the WebSocket is the direct connection.
  • Web push notifications for direct devices (there is nothing to push through).
  • Several direct bridges in one page (each bridge serves its own origin; cross-origin pairing is a follow-on, §14).
  • Passkeys against the bridge as a WebAuthn relying party (possible later on top of the same listener).

Compare the hosted path (README.md diagram): api for login and the SPA, relay for rendezvous, Cloudflare TURN when peers cannot hole-punch. None of it appears here. The same bridge binary can run both paths at once; a browser on the hosted path and a phone on the direct path are simply two clients with two different ways of proving who they are.

3. Trust model

On the hosted path the bridge never authenticates a user. It trusts the relay to admit only the device owner (same-owner scoping on session_init) and trusts the api to have pinned its transport key for the browser. Remove Build and both guarantees vanish, so the direct path rebuilds them at the bridge, mirroring what the api does today with device identity keys:

QuestionHosted pathDirect path
Is this the right bridge?api pins transport_public_key_b64; browser seals to itinvite carries the bridge identity fingerprint; bridge proves possession with a signed challenge; browser pins it
Is this browser allowed?relay checks gateway token → user → device ownerbridge checks the client's identity key against its authorized_clients
Who registered whom?pairing code redeemed at the apione-time invite secret minted by the bridge CLI, consumed on first use
Wire confidentialityE2EE envelope over relay / DTLSE2EE envelope over WSS over WireGuard (unchanged envelope, PROTOCOL_VERSION 1)
Revocationapi revokes devicebridge revokes client (CLI + settings)
Rule 1. The bridge is its own registry. ~/.build/direct/authorized_clients.json is the only authority for who may open a direct session. No file, header, or tailnet identity replaces it.
Rule 2. The E2EE session is unchanged. A direct session is minted with the same session_init / session_accept, sealed to the same transport key, carried by the existing socket carrier. Nothing is ever plaintext on the wire, even inside the tailnet.

4. The invite

build-bridge direct invite [--name "Alice's phone"] [--ttl 10m] prints a compact string and a QR code. It is not a JWT: the browser has no prior trust in any key, so a signature proves nothing at this point. The invite is a bootstrap credential: it tells the browser where the bridge is, which key to expect, and gives it one secret to prove it was invited. 

{
  "v": 1,
  "addr": ["https://box.tail1234.ts.net"],        // one or more origins, tried in order
  "fp":   "sha256:9f3c…a1",                        // bridge identity public key fingerprint
  "secret": "base64url(32 random bytes)",          // one-time, ≥ 256 bits
  "exp":  1758000000,                              // unix seconds; default now + 10 min
  "name": "Alice's phone"                           // label the bridge will store for this client
}
→ encoded as base64url(JSON), shown as text and as  build-direct://<encoded>
→ the QR carries  https://box.tail1234.ts.net/#invite=<encoded>   (fragment, never query string)
  • The secret is machine-generated and pasted or scanned, never typed, so it can be long. A long secret needs no PAKE: the paste/scan channel is assumed confidential, the same assumption an SSH key or WireGuard config makes.
  • Single use. The bridge stores hash(secret), exp, name; a redeemed or expired invite is deleted. build-bridge direct invites lists pending ones; direct invite --revoke <id> cancels.
  • The fragment form exists so a scanned QR can open the SPA with the invite without the invite ever reaching a server log or a Referer header. The SPA reads and clears location.hash before doing anything else.

5. Pairing handshake

Over WSS /direct/pair, JSON frames, all bounded to 16 KiB. The browser first generates its own long-lived Ed25519 client identity keypair (libsodium, stored in IndexedDB).

1client → bridge: {"type":"pair_hello","client_nonce":n_c} 2bridge → client: {"type":"pair_challenge","bridge_nonce":n_b,"identity_public_key":pk_b,"sig":Sign(sk_b, "direct-pair-v1" ‖ n_c ‖ n_b ‖ pk_b)} 3client verifies sha256(pk_b) == fp from the invite and the signature. On mismatch it stops and shows "this is not the bridge the invite came from". The bridge key is now pinned. 4client → bridge: {"type":"pair_prove","client_public_key":pk_c,"name":name,"mac":HMAC(secret, "direct-pair-v1" ‖ n_c ‖ n_b ‖ pk_b ‖ pk_c ‖ name)} 5bridge looks up a pending invite whose secret verifies the MAC (constant-time), checks exp, then appends {pk_c, name, paired_at, last_seen} to authorized_clients, deletes the invite, and notifies the desktop ("Alice's phone paired"). 6bridge → client: {"type":"pair_ok","transport_public_key":tpk_b,"sig":Sign(sk_b, "direct-pair-ok-v1" ‖ n_c ‖ n_b ‖ tpk_b ‖ pk_c)} 7client verifies and stores {origin, fp, tpk_b, own keypair, bridge name} as a direct device record. Pairing is complete; the socket closes.
  • The MAC binds the client key and both nonces to the invite, so a captured invite cannot be replayed to enrol a second key, and an attacker on the path cannot swap pk_c.
  • Rate limits: 5 failed pair_prove per source address per minute, then a 15-minute lockout; every failure is logged with the source address.
  • The bridge's identity key is the same one it uses with the api (identity.rs); the direct path does not mint a second identity. The transport keypair is likewise shared.

6. Sessions after pairing

Over WSS /direct/ws. The browser opens the socket and sends, for each session it wants:

{
  "type": "session_init",
  "session_id": "sess-…",
  "session_init": <the existing sealed session_init, sealed to tpk_b>,
  "client_public_key": pk_c,
  "timestamp": 1758000123,
  "sig": Sign(sk_c, "direct-session-v1" ‖ session_id ‖ fp ‖ timestamp ‖ sha256(session_init))
}
  1. The bridge refuses unless pk_c ∈ authorized_clients, |now − timestamp| ≤ 60 s, the signature verifies, and (pk_c, timestamp, sig) has not been seen (replay guard, 2× the window — the same scheme as the relay's device auth and the api's notify route).
  2. Then FrameIntake::open runs unchanged and session_accept returns over the same socket — the carrier-neutral seam the strict-P2P change built for exactly this.
  3. The socket is a CarrierKind::Direct. Unlike the relay carrier it carries everything: there is no data-plane refusal, because the bridge authenticated this client itself.
  4. Re-attach on a new socket repeats the same frame with the same session id and key, as on the hosted path. A session ends when its last carrier ends or its client says so (registry rule unchanged).
  5. last_seen on the client record is updated on every accepted session_init; the settings page shows it beside the Revoke button. Revoking a client ends its live sessions immediately (SessionRegistry::end for every session admitted under that key).

7. The bridge listener and TLS

Rule 3. The direct listener is off until the first invite is minted and binds to loopback only unless a certificate pair is configured. Tailscale terminates TLS; the bridge never serves plain HTTP on a non-loopback address.
SettingDefaultMeaning
BRIDGE_DIRECT_LISTEN127.0.0.1:7800Where the embedded SPA and /direct/* are served. A non-loopback address is refused unless the cert pair below is set.
BRIDGE_DIRECT_TLS_CERT / _KEYunsetEscape hatch: the bridge terminates TLS itself from files (e.g. from tailscale cert box.tail1234.ts.net). Reloaded on SIGHUP.
BRIDGE_DIRECT_ORIGINderived from the first invite's addrThe one Origin/Host the listener accepts (DNS-rebinding defence). Requests with any other Host are answered 421.
BRIDGE_DIRECT_TAILNET_USERSunset (no check)Optional allow-list of tailnet logins; see §9.

The recommended setup is one command, which the bridge prints after direct invite:

tailscale serve --bg https / http://127.0.0.1:7800

This gives https://<box>.<tailnet>.ts.net a Let's Encrypt certificate that every browser trusts (requires MagicDNS and HTTPS certificates enabled on the tailnet, which Tailscale prompts for). Because tailscale serve proxies from the tailnet to loopback, the port is unreachable from any other network. The bridge detects the proxy by the loopback peer address plus the Tailscale-User-Login header and treats that header as trustworthy only on loopback connections.

Why not bare LAN yet: an https:// page cannot open ws://192.168.1.5 (mixed content), and a self-signed wss:// needs a trust dialog on every device, which on iOS means installing a profile. Serving plain http:// on a LAN would let anyone on that network substitute the page and steal the client key. A tailnet has neither problem.

8. The SPA in direct mode

The same build is embedded in the bridge (include_dir! of skriftapp/buildapp/static/ at compile time, so spa/ keeps building into one place). At boot the SPA decides which mode it is in:

direct mode  ⇔  document has <meta name="build-mode" content="direct">   (the bridge injects it)
             ⇔  never: fetch("/api/…"), passkeys, gateway tokens, ICE servers, push subscribe
  • Rendezvous. core/rendezvous.js gains createDirectRendezvous({origin, record}): open() dials /direct/ws, mint() sends the signed session_init of §6, and — unlike the relay rendezvous — the socket is the carrier, so signalCarrier is unused and the session switch is told peer(socketCarrier) directly. No peer link is ever opened.
  • Device identity. A direct device's deviceId is direct:<fp>. Device contexts, device keys (${deviceId}/${projectId}), routes and caches work unchanged.
  • Presence. No api poll. A direct device is online while its socket answers ping (the terminal socket's liveness rule, 4 s); reconnect with backoff 1 s → 15 s; away while it does not.
  • New device screen. Settings → Devices → Add a direct connection: a paste field for the invite (or the fragment form on load). It shows the bridge's name and fingerprint before pairing, then the pairing result. Records are listed with Forget.
  • Storage. Client keypair and device records in IndexedDB under the bridge's origin. The private key never leaves the page; export is not offered.
  • Gate. The login/passkey gate is skipped; the waiting screen's copy names the bridge ("Waiting for box on your tailnet").
  • Fail closed. No code path in direct mode may construct a relay URL, call fetchIceServers, or read VITE_RELAY_URL; a source-scan test pins it, like noCurrentDevice.test.js pins the retired singletons.

9. Tailnet integration

  • Detection. The bridge asks tailscale status --json at start (if the binary exists) for its own .ts.net name and address, uses them in invites, and prints the serve command.
  • Identity allow-list (optional). With BRIDGE_DIRECT_TAILNET_USERS=alice@github the bridge requires, on /direct/pair and /direct/ws, that tailscale whois <peer-ip> (or the Tailscale-User-Login header from the loopback proxy) names an allowed login. This runs before the client-key check and never replaces it.
  • Headscale and other control planes work the same; nothing here talks to Tailscale's servers except tailscaled itself.
  • Docs. deploy/README.md gains "Direct connections over Tailscale": install Tailscale on the machine and the phone, mint an invite, run the serve command, scan the QR.

10. Mobile

  • iOS and Android run the Tailscale app from their stores; nothing of ours is installed.
  • Install the SPA to the home screen (PWA). Safari's storage eviction after 7 days of non-use does not apply to installed web apps, so the client key survives; if it is evicted anyway, pairing again is one scan.
  • The QR fragment flow means pairing from a phone is: open camera → scan → confirm the fingerprint shown → done.
  • No notifications in direct mode (documented on the settings page). A later revision may deliver them through the socket while the PWA is open.

11. Threat model

Amends build-secure-transport/E2E-MVP.md with a new party, the local network / tailnet, and removes two (relay, Cloudflare) from the direct path.

AttackerCanCannot, and why
Someone on the same tailnet (a shared or compromised node)Reach the port; see TLS metadata; attempt pairingOpen a session: no authorized key. Pair: no invite secret (256-bit, single use, rate-limited). Substitute the bridge: the page is served over Tailscale's cert and the invite pins the identity fingerprint.
Someone who obtains an invite (shoulder-surfed QR, pasted into the wrong chat)Pair one client within the TTL if the real user has not yetPair after the real user did (single use); the desktop notification and the clients list expose the extra client, which is revoked in one click. Mitigation: short TTL, the SPA shows the bridge name/fingerprint before it proves.
Someone who steals the phone (unlocked)Use the paired sessionPersist after revocation: the bridge ends its sessions and refuses its key. The client key is not exportable through the UI.
Tailscale (the control plane)See node keys and tailnet membership; route WireGuardRead anything: WireGuard is end-to-end between the two nodes, TLS is on top, and the E2EE envelope is on top of that. Impersonate the bridge: the pin is on the bridge's own identity key, not its tailnet address.
Build (us)Nothing: not in the path—
A malicious page in the same browserAttempt DNS rebinding or cross-origin WebSocketThe listener answers only its configured Origin/Host; the key lives under the bridge's origin; no cookies are used.
Residual. A compromised tailnet node that also obtains a live invite within its TTL can enrol itself. The controls are TTL, single use, the pairing notification, and the clients list. Accepting this is the same choice SSH makes with authorized_keys.

12. Security checklist

To be scored 100/100 before the feature ships, in the style of the existing checklists in planning/v2/.

  1. Listener off by default; loopback-only without a cert pair; never 0.0.0.0.
  2. Origin and Host pinned; 421 otherwise; no cookies; no CORS headers.
  3. Invite secret ≥ 256 bits from the OS CSPRNG; stored hashed; single use; TTL ≤ 10 min by default, max 24 h.
  4. Pairing MAC binds both nonces, the bridge identity key, the client key and the name; verified in constant time.
  5. Bridge proves identity-key possession before the client sends anything secret-derived.
  6. session_init signed by an authorized client key with a 60 s window and a replay guard.
  7. Rate limit and lockout on pairing; every refusal logged with the source address.
  8. Revocation ends live sessions immediately and is available from the CLI and the settings page.
  9. The tailnet identity check, when enabled, runs before the key check and never replaces it; the header is trusted only from loopback.
  10. Direct mode has no code path to the relay, api, ICE servers or push; a source-scan test enforces it.
  11. All direct frames bounded (16 KiB pairing, 8 MiB session, the same reassembly cap as the channels).
  12. Client key non-exportable through the UI; stored under the bridge origin only.
  13. The E2EE envelope is unchanged; interop_python.rs keeps passing.
  14. Threat-model amendment landed in build-secure-transport/E2E-MVP.md (separate repo) and referenced from README.

14. Open questions

  1. Should a hosted-path browser (page from getbuild.ing) be allowed to also hold direct devices? It would need cross-origin WSS to the bridge, which the pairing permits, but the page itself is Build's. This spec says no; the guarantee is per page.
  2. Several direct bridges in one page: each is its own origin today. A follow-on could let one bridge's page pair with another bridge (cross-origin WSS + the same invite), giving the multi-device board without any server.
  3. Invite TTL default: 10 minutes, or shorter?
  4. Should revoking the last client turn the listener off again?
