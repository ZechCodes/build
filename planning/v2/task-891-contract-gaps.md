## Existing guarantees and notation

`tasks.list {project_id,summary:true,limit,cursor?,…}` is advertised by `tasks.listSummaries`. It accepts state/status/label/assignee scalar or plural selections, OR within a dimension and AND across dimensions. See `bridge/src/app/tracker/selections.rs:6`, `:14`, `:65`; dispatch is `bridge/src/app/tracker/read.rs:127`. There is no watched, tracker, linked-workspace, number, text, attention, done-since, or sort selector in that parser. Unknown fields must not be mistaken for working filters.

**S (existing summary bounds):** default 100, maximum 500 rows; at most `4*limit+1` candidate rows per request, fetched in chunks of at most 32; at most 1,048,576 serialized bytes; row plus identity contribution at most 65,536 bytes; at most 1,000 shared identities. Empty pages with continuation are valid. Order is task number descending. See `docs/bounded-task-reads.md` and `bridge/src/app/tracker/summaries.rs:58`. Current summary SQL seeks `(project_key,number)` and applies selections to candidates; sparse selections can need many continuation requests. A request bound does not establish completeness of an entire selected set.

**P (proposed selected-page bounds):** reuse S's defaults, row/response/identity byte limits and opaque, selection-bound cursor rules. Prefer an exact membership index reading at most `limit+1` selected records; if post-filtering is necessary, retain an explicit `4*limit+1` candidate budget and empty-page continuation. Never silently skip oversized records or decode history. No background cursor exhaustion. A positive `next_cursor` means a view is incomplete; showing a loaded count is distinct from an exact total.

**A (proposed aggregate bounds):** one project total plus at most 100 explicitly requested agent buckets, at most 65,536 serialized bytes. Point reads of at most 101 materialized aggregate records; no runtime `SUM` over every project task, full roster, or history. Reject oversized requests. Return a publication/basis token so cache refresh and newer local read/watch effects cannot double-adjust a total. Larger caller sets require explicitly bounded batches; the client must not call a partial batch a complete workspace total.

Producer abbreviations below refer to existing hooks in `bridge/src/store/task_summaries/maintenance.rs`: **T** `task_written`/`task_remove` (`:71`, `:118`), **H** `history_append`/`history_repair` (`:177`, `:209`), **D** `dependency_refresh`/`task_dependents_refresh` (`:164`, `:141`), **M** `metadata_refresh` (`:157`). These are Rust producer hooks in the canonical transaction, not independent-SQL triggers (`:1`). Proposed derived records must participate in startup backfill/repair, imports, deletion and reparenting as documented in `docs/bounded-task-reads.md`. Index ownership below describes required work; those indexes/aggregates do not already exist unless explicitly identified.

## Cache and compatibility requirements independent of API choices

- No page subset is a whole-project replacement. Store summary identity separately from query membership; absence from a page is unknown. Cursor identity includes mode, canonical selections and ordering. Existing summary cursors can terminate in an empty page with continuation.
- Display truncation is not relation truncation. `summary_truncated:true` must never overwrite full detail or prove a missing tracker/workspace membership. Summary title search cannot silently ignore canonical title text after the 1,024-character display cap.
- `trackerTaskDetailsFeed.js:72` limits concurrency to four but `:103` eventually requests `tasks.get` for every queued task. Removing this fan-out for summary-capable list/Inbox paths is required independently of timeline API approval. Cached newer detail/read markers still need precedence over stale summary counters (`taskUnread.js:40`).
- Proposed aggregate/membership indexes must be maintained by supported Rust producers in the same transaction as canonical changes. Startup migration/backfill, independent-SQL repair/import ownership, failure rollback, and deletion/reparenting tests are part of each approved bridge slice. A normal page must not rebuild projections or load canonical bodies/history.
- `spa/src/core/bridgeApi/v1/index.js:177` currently exposes neither `tasks.listSummaries` nor `tasks.filterChoices`; add explicit capability mapping before dispatch. Rendering comes from persisted cache/support records; live greeting controls dispatch. Do not silently send proposed selector fields to a bridge that only advertises summaries.
- Existing APIs are enough for bounded project list/board pages, assigned-only workspace pages, per-loaded-task summary counters, and filter choices. They are insufficient to preserve complete project aggregates, arbitrary watched/linked/tracked membership, number reference resolution and unbounded detail/timeline semantics without additional decisions. Exact global ordering of grouped surfaces is a separate issue from membership.

## Suggested decision boundary

Approve only the needed primitive additions, each with its own contract witness and producer/index coverage. Counts, watched membership, attention membership, linked-workspace membership, and tracker membership are different predicates and should not be hidden behind a single semantic “surface” query. Confirm whether dashboard/overview/agent ordering and large detail/history are required to remain globally complete before describing #891 as fully complete. A UI that labels a partial set as complete is not a compatible bounded implementation.
